# 4.3.1 修复与验证记录

日期：2026-11-11。4.3.1 / versionCode=31 是图片清理安全性补丁：修复 4.3.0 在系统备份恢复与数据库读取异常场景下可能误删已保存事件配图的路径。物理真机未执行，按发布负责人授权如实记录。

## 问题与根因

用户报告的触发条件：应用启动清理时，如果读取事件图片引用失败，代码会把引用当成空集合，符合清理条件的已保存事件图片可能被删除；另一路清理也可能删除保存超过 7 天的未完成草稿图片。

代码核对确认：

1. `EventImages.kt` 的 `cleanupRegisteredImages` 使用 `runCatching { referencedFiles() }.getOrDefault(emptySet())`，数据库读取失败会被静默降级为空集合。
2. `sweepUnreferencedImages` 仅以该集合判断“未引用”，并以 7 天 mtime 为门槛删除 `event_images/` 下的应用生成文件；注册表位于 `noBackupFilesDir`，不随系统备份迁移，恢复后可能为空。
3. 启动清理在 `TimeApplication.onCreate` 立即排队，备份恢复期间数据库可能尚未就绪。

影响范围是应用内保存的图片副本（`files/event_images/`），不是相册原图；未能在 Android 设备上复现实际丢失。

## 修复内容

- **读取失败不再降级为空集合**：`cleanupRegisteredImages` 读取引用失败时抛出异常并终止本次清理；调用方捕获后记录日志，等待下一次启动重试。
- **数据库底线校验**：`sweepUnreferencedImages` 在删除前通过 `AppDatabase` 查询全部事件的 `imagePath`，即使清理注册表丢失，只要文件仍被任何事件引用就不会删除。
- **重试与启动缓冲**：`TimeApplication` 启动清理延迟 1 秒，并对事件快照读取做 5 次、每次 2 秒的重试；失败则安全退出。
- **测试**：新增 `EventImageRegistryTest.databaseReadFailurePreservesAllCandidates`，覆盖“读取引用抛异常时不得删除候选图片”。
